# Findings — Meilenstein 2

Format: `- [ ] → Phase N: <Erkenntnis>` — offen, bis die betroffene Phase sie eingearbeitet hat.

- [x] → Phase 2, 4: Neue Listen-Tabellen gehören an zwei Stellen eingetragen: `RecordMerger::TABLES` (Schlüssel, abgleichbare Spalten) und `RecordRepository::ORDER` (Sortierung). Das Repository hat keinen `$orderBy`-Parameter (Abweichung von der Phasen-Datei, Sortierung bleibt Konstante). Phase 2: Ereignisse laufen über das eigene `EventRepository` (Lesen mit Werkstatt-Join), nur `TABLES` ist ergänzt. Phase 4 prüft für Messwerte/Reifen/Teile/Schäden selbst, ob `RecordRepository::ORDER` reicht.
- [ ] → Phase 5: Die Prüfung von `open_items.proposal_json` und `audit_log.vehicle_id` ist in Phase 1 und 2 nur im Code belegt (kein Lese-Zugang von außen). Sobald der Verlauf/die Klärfall-Liste Daten liefert, per `curl` gegenprüfen — auch die Vorschläge der Phase 2 (`proposal.items` bei Positionen, `proposal.conflicts_with` bei Kilometerständen). Die JSON-Spalte sortiert Objektschlüssel um: Vergleiche über `EventService::sortedKeys`, nie über die Schlüsselreihenfolge.
- [ ] → Phase 3: Die Fälligkeit liest Kilometerstände nur über `OdometerService::validReadings` (Status `gueltig`, strittige und verworfene Stände zählen nicht). Ausführungen kommen aus `events` + `event_items.task_key` (Spalte seit Migration 009 vorhanden, noch ohne Bezug zu `tasks`).

Dazu zwei nie angenommene Einladungen („Probe“, „Probe2“, laufen nach 7 Tagen ab).
